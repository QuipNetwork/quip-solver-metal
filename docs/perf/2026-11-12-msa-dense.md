# Dense-matrix multi-spin measurements, 2026-11-12

The dense-matrix multi-spin kernel, `kernels/msa_dense.metal`, reads one row of an `N * N` coupling matrix for each update. One threadgroup of this kernel walks between 70 and 232 million matrix columns per second on average. The rate depends on the precision and the size. The slowest single chunk ran at 68.2 million columns per second: one sweep of the Int32 model of 6,016 nodes, 530.8 ms. The chunk planner plans at 60 million columns per second for each threadgroup with a 0.4 margin (`MSA_MATRIX_COLUMNS_PER_SEC = 6.0e7`, `MSA_MATRIX_THROUGHPUT_SAFETY = 0.4`). The value 6.0e7 is the quiet-GPU worst chunk rate of 68.2 million, less a margin for contention from other GPU work. Where a chunk holds more than one sweep, the worst measured chunk was 208.2 ms, Int8 at 64 nodes. A chunk holds at least one sweep, so the admission refuses a dense-matrix model whose one sweep the planner estimates at more than 400 ms. That limit is 4,898 nodes at every precision and read count. The margin comes from 5,099 nodes, the limit at 6.5e7: one Int32 sweep of 256 reads measured 380.0 to 380.7 ms on three of five runs, and 408.2 and 467.3 ms on the two runs with the most load from other agents.

## Host and load

The host was an Apple M4 Max with 40 GPU cores, measured on 2026-11-12 between 01:25 and 01:33 local time. Other agents used the host during the run. The one-minute load average was 8.2 shortly after the run.

## Commands and method

```sh
cargo test --release --test msa_dense dense_rates -- --ignored --nocapture
```

`dense_rates` in `tests/msa_dense.rs` runs complete models with a planted ground state at each precision. Every run has 256 reads, the batch path's read cap (`MAX_READS`), which is 8 threadgroups of 32 reads. The test checks that all 256 reads come back. It uses the production chunk plan and records the total GPU time, the chunk count, and the longest chunk's GPU time.

One column update is one word update times one matrix column. A sweep of an `N`-node model is `8 * N * N` column updates. The rate column divides the column updates by the GPU time and by the 8 threadgroups.

The measured run planned at 7.1e7 columns per second. The value in the code is 6.0e7, so production chunks are about 15 percent shorter than the measured chunks. The run also took the 5,600-node and 6,016-node models, which the admission now refuses. The test now stops at 4,898 nodes.

## One-sweep limit

From 4,096 nodes up, every chunk is one sweep, so the planner cannot shorten it. The longest one-sweep chunk grows with the square of the node count. Scaled from 4,800 nodes, one sweep reaches 400 ms at these sizes:

| Precision | Longest chunk at 4,800 nodes, ms | Nodes at 400 ms |
| --- | --- | --- |
| Binary | 135.5 | about 8,200 |
| Int8 | 299.7 | about 5,500 |
| Int32 | 344.4 | about 5,200 |
| Float32 | 316.8 | about 5,400 |

The measured 5,600-node chunks agree: 455.9 ms for Int32 and 420.2 ms for Float32. The Int8 estimate is low. The measured Int8 chunk at 6,016 nodes was 393.9 ms. The Binary size is an extrapolation past the measured range.

## Admission limit for one sweep

The admission estimates one sweep as `N * N` columns at 6.0e7 columns per second, without the planning margin. The planner uses the same constant. Every threadgroup walks its rows at once, so the estimate does not depend on the read count. The estimate passes 400 ms past 4,898 nodes (4,898 nodes give 399.84 ms and 4,899 nodes give 400.003 ms). The admission refuses a model past the limit with `SampleError::TooLarge`, which the harness reports as `Capacity`, before any buffer exists.

```sh
cargo test --release --test msa_dense the_largest_admitted_dense_sweep_runs -- --ignored --nocapture
```

The test runs a complete Int32 model of 4,898 nodes with 256 reads and two sweeps, one sweep per chunk, and checks that the admission refuses 4,899 nodes. On the M4 Max, in a gate run on 2026-11-12 with other agents using the host, the longest chunk at 4,898 nodes measured 350.3 ms. The load average of that run was not recorded.

An earlier limit of 6.5e7, at 5,099 nodes, shows why the margin exists. Five runs of the 5,099-node test between 02:05 and 02:07 local time, with a one-minute load average of 10.2 to 13.5, gave these longest chunks: 380.0, 380.5, 380.7, 408.2, and 467.3 ms. The quiet runs equal 68.4 million columns per second, which agrees with the 6,016-node chunk. The two slow runs shared the GPU with other agents and passed 400 ms. At 6.0e7, a sweep at the limit is 0.92 times as long as at 5,099 nodes, so the same 467.3 ms of contention would scale to about 430 ms. The margin covers the quiet rate with room for moderate contention, not for every load.

The limit is the same for every precision. Binary sweeps ran at about 214 million columns per second at large sizes, so the limit refuses Binary models whose sweep would take about 110 ms. A separate Binary rate would admit them, but this document has no Binary measurement past 6,016 nodes.

## Why the rate does not use the occupancy curve

Each threadgroup of the dense-matrix kernel is one SIMD group, 32 threads that run in lockstep. The SIMD group visits the nodes of a color class in order, and a complete model has one node in each class. The column walk of one node is a chain of dependent additions, so its speed depends on latency, not on how many cores the GPU has. The planner multiplies a fixed rate by the threadgroup count. It does not read `MSA_OCCUPANCY_CURVE`, which is a rate for each GPU core.

On a slower GPU each SIMD group takes longer, and the chunks grow by the same ratio. This document has no measurement of that ratio.
