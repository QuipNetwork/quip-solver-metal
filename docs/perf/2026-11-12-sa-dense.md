# Dense matrix simulated annealing measurements, 2026-11-12

The dense-matrix SA kernel, `kernels/sa_dense.metal`, reads one row of an `N * N` coupling matrix each time a spin flips. It returns the same reads as the sparse SA kernel for the same seed. The cost of a sweep depends on how many spins flip, because a flip walks `N` matrix columns and a rejected update does not. The sweeps at the hot start of the schedule are the slowest, so the rate in the code comes from them.

The slowest single chunk ran at 5.76 million column walks per second: one sweep of the Int8 model of 4,898 nodes, 4,165 ms. The planner and the admission limit both use one constant, `SA_MATRIX_COLUMNS_PER_SEC = 5.0e6`, which is 13 percent under that rate. The constant is a per-chunk worst case, taken at the hot start of the schedule where most spins flip. The rates in the tables are averages over a whole run, about 6 to 17 times higher, because most sweeps are colder than the hot start. That is why the plan holds one sweep per chunk at 1,024 nodes and more. A chunk holds at least one sweep, so the admission refuses a dense-matrix SA model whose one sweep the planner estimates at more than 400 ms. That limit is 1,414 nodes at every precision and read count. At the limit, the longest measured chunk was 328.5 ms (Int8 and Binary models, one sweep). Where a chunk holds more than one sweep, the longest measured chunk was 170.1 ms, at 1,024 nodes.

The limit is low because memory latency limits the kernel. One flip of a 1,414-node model reads and writes 1,414 deltas per read, and each SIMD group of 32 reads does this at about 6 to 10 million column walks per second.

## Host and load

The host was an Apple M4 Max with 40 GPU cores. The runs took place on 2026-11-12 between 02:55 and 03:15 local time. Other agents used the host during the runs. The one-minute load average was between 5.4 and 6.0 shortly after the runs.

## Commands and method

```sh
cargo test --release --test sa_dense dense_rates -- --ignored --nocapture
cargo test --release --test sa_dense the_largest_admitted_dense_sweep_runs -- --ignored --nocapture
```

`dense_rates` in `tests/sa_dense.rs` runs complete models with a planted ground state at each precision. Every run has 256 reads, the batch path's read cap (`MAX_READS`). The test checks that all 256 reads come back. It uses the production chunk plan and the default beta schedule, and it records the total GPU time, the chunk count, and the longest chunk's GPU time.

One column walk is one flip times one matrix column. The rate column assumes that every spin flips in every sweep, so a sweep of an `N`-node model counts as `N * N` columns. The number is a lower bound on the true rate when few spins flip, and close to exact at the hot start. The rate divides the columns by the total GPU time, so it averages hot and cold sweeps. The slowest chunk runs at a lower rate.

The kernel is the same at every read count up to 256. The SIMD groups of a dispatch run side by side, so the time of one sweep does not depend on the read count. Splitting the 256 reads into eight threadgroups of one SIMD group each, instead of one threadgroup, did not change the rates.

## One-sweep limit

The admission estimates one sweep as `N * N` column walks at 5.0e6 column walks per second, without the planning margin. Every SIMD group walks its rows at once, so the estimate does not depend on the read count. The estimate passes 400 ms past 1,414 nodes (1,414 nodes give 399.88 ms and 1,415 nodes give 400.445 ms). The admission refuses a model past the limit with `SampleError::TooLarge`, which the harness reports as `Capacity`, before any buffer exists. Auto and forced dense both refuse. The unit test `a_dense_sa_sweep_past_one_chunk_is_refused_before_allocation` in `src/sampler.rs` checks both sides of the limit, and `a_model_past_the_sweep_limit_is_refused_under_auto_and_forced_dense` in `tests/sa_dense.rs` runs the refusal through the sampler.

At the limit, one sweep of an Int32 model of 1,414 nodes with 256 reads measured 182.4 ms in `the_largest_admitted_dense_sweep_runs`. The Int8 and Binary models measured 327.0 and 328.5 ms in `dense_rates`. The margin of the slowest shape under 400 ms is 18 percent. It covers the quiet rate with room for light contention, and it does not cover every load.

## Why the rate is below the multi-spin kernel

The dense multi-spin kernel runs at 68.2 million column walks per second for each threadgroup of 32 replicas, and the dense SA rate is per dispatch of 256 reads whose SIMD groups run side by side, so both rates measure 32 reads. One SIMD lane of the multi-spin kernel holds one replica of a 32-replica word, so one column costs one register operation on spin words kept in threadgroup memory, and the walk runs on every word update. The dense SA kernel keeps a separate `delta_energy` value for every spin of every read in device memory, so each column costs a load and a store at a different address in each of the 32 lanes, and the walk runs only when a spin flips. Memory latency, not arithmetic, sets the rate, which is about 12 times lower than the multi-spin rate.

## Dense against sparse

The sparse SA build ran the same models with the same seed and returned the same reads, so the work is equal and the GPU times compare directly. The sparse runs used `Tuning::force_sparse`, with the production chunk plan. The command is:

```sh
cargo test --release --test sa_dense sparse_rates -- --ignored --nocapture
```

Rates are in millions of column walks per second over the whole run, as in the earlier tables. The host and the load are the same as in the earlier sections, and the sparse runs took place at 03:25 to 03:35.

| Precision | Nodes | Dense GPU ms | Dense rate | Sparse GPU ms | Sparse rate | Sparse longest chunk ms |
| --- | --- | --- | --- | --- | --- | --- |
| Int8 | 1,024 | 20,036 | 53.6 | 24,381 | 44.0 | 4,165 |
| Int8 | 1,414 | 3,555 | 51.7 | 4,281 | 43.0 | 4,261 |
| Int32 | 1,024 | 11,154 | 96.3 | 21,970 | 48.9 | 4,235 |
| Int32 | 1,414 | 2,002 | 91.9 | 3,872 | 47.5 | 3,852 |

Dense was not slower than sparse at any of these sizes. Dense ran 1.2 times faster for Int8 and 1.9 to 2.0 times faster for Int32. The sparse chunks were 3.9 to 5.1 seconds long, because the sparse chunk plan does not model a complete model. That is the open sparse one-sweep floor on bead `quip-miner-metal-dvg`, which this change does not address.

Sparse storage ran larger models than the dense limit allows, with chunks of 4 to 5 seconds. A complete Int8 model of 2,500 nodes ran in 5,146 ms of GPU time in two chunks (31.6 million column walks per second, longest chunk 5,140 ms), and Int32 in 4,961 ms (32.8, 4,954 ms). A complete Int8 model of 4,898 nodes does not fit on sparse storage: it needs 60.1 GB against 55.0 GB usable on this host. Dense storage fits it, but the one-sweep limit refuses it.

## Effect on routing

The capacity model routes a model to dense storage when the dense matrix takes fewer bytes than the CSR arrays. For SA this happens for models with more than about a fifth of the possible couplers, or half for Int32 and Float32. A routed model of more than 1,414 nodes now gets a `Capacity` refusal under Auto and under forced dense.

Before this kernel, at commit cb0ea52, the sparse build accepted some of these models. It accepted them only by committing planned command buffers of 3.9 to 5.1 seconds, against a plan that expected 500 ms. The `sparse_rates` command in the section on dense against sparse reproduces those chunks. The sparse SA cost in the planner has no term for the degree of the model, so it plans too much work per chunk on a complete graph (bead `quip-miner-metal-9sp`). A planner fix or a sparse one-sweep check would be a separate change, tracked outside this document.

## Rates and the sweep change of November 12

The rates and chunk times in this file come from runs before QUI-2265 (merge request !33 on main). Since that change, every sweep of an anneal except the last leaves one node out, in the dense kernel as in the sparse kernel, so the two kernels still return the same reads. The change removes at most one node update per sweep, so the planner constants keep their values. Nobody measured the rates again.
