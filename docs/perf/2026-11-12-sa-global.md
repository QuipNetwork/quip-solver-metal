# Global-state measurements for simulated annealing, 2026-11-12

The simulated annealing (SA) kernel has a global-state build, `QUIP_SA_GLOBAL`, for models past its 4,593-node thread-private frame. The build keeps each read's packed spins and `delta_energy` in the persistent buffers, interleaved by thread. On 4,000-node models the global build updates spins 12 to 21 percent slower than the local build. On larger models the rate falls further, so the chunk planner multiplies the SA cost by `SA_GLOBAL_COST_FACTOR = 2.0` on the global build. The largest planned chunk was 127 ms for models of 20,000 nodes and 256 reads. Models of at most 4,593 nodes keep the local build, and the SA digest `e4e22f86b64cda5d` does not change.

## Host and load

The host was an Apple M4 Max with 128 GiB of memory, measured on 2026-11-11 between 22:23 and 23:05 local time. Other agents used the host during every run. The one-minute load average was between 5.5 and 11.1.

## Commands and method

```sh
cargo test --release --test sa_capacity -- --ignored --nocapture --test-threads=1 global_state_rates
```

`global_state_rates` in `tests/sa_capacity.rs` runs circulant models with 256 sweeps at 4 sweeps per rung, on four coefficient paths. The unit path runs the int8 build. Two milli paths run on `int` and `int8_t` storage. The last path is Float32. For each model it records the median GPU time of three runs in one command buffer, and the spin updates per second, where one update advances one read by one spin. It then runs the model with the production chunk plan and records the chunk count and the largest chunk's GPU time. A 4,000-node model runs on both builds. A larger model runs only on the global build.

At degree 40 and 20,000 nodes the global rate is 0.0975 to 0.1062 Gupd/s, about half the degree-20 rate, because each flip updates twice as many neighbours.

## Chunks

The planned runs used the cost factor of 2.0. A rung splits into sweep windows when one rung exceeds a dispatch's budget, as on the weighted multi-spin kernel.

| Nodes | Degree | Reads | Chunks | Largest chunk ms, by path (unit, `int`, `int8_t`, Float32) |
| --- | --- | --- | --- | --- |
| 4,000 | 20 | 256 | 64 | 28.8, 31.2, 30.7, 53.2 |
| 4,000 | 20 | 1,024 | 64 | 28.8, 31.2, 30.7, 30.8 |
| 20,000 | 20 | 256 | 256 | 56.9, 68.7, 62.1, 68.3 |
| 20,000 | 40 | 256 | 256 | 103.8, 123.1, 106.6, 126.5 |
| 60,000 | 20 | 1,024 | 256 | 186.7, 208.6, 188.3, 271.6 |

Every model past 4,000 nodes ran one sweep per chunk, which is the smallest chunk the planner makes. The 60,000-node model with 1,024 reads is at that limit: one sweep of that model takes about 200 ms. Its largest Float32 chunk was 271.6 ms in this run and 203.0 ms in an earlier run of the same command under the same load. The planner does not split one sweep, so a model whose sweep costs more than the 500 ms ceiling would pass it. The memory footprint still admits such a model.

## Device energy

The local int8 build computes a device energy that the host never reads, because the host scores every SA read. The global build skips that computation. In the earlier run, which still had the computation, the largest unit chunk on the 60,000-node model was 333.3 ms. Without it, the largest unit chunk was 186.7 ms. The reads do not change, because the energy does not take part in any flip decision.
